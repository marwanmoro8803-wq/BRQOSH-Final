# ADR-002: المعمارية النظيفة والوحدات القابلة للتفعيل

**الحالة:** معتمد
**التاريخ:** 2026-07-05

## السياق

البرنامج يبدأ باختيار **نظام العمل** عند أول تشغيل، ثم تُفعَّل الوحدات المناسبة.
يجب أن تكون الوحدات معزولة بحيث لا يؤثر تعطيل وحدة على النواة أو وحدة أخرى.

## القرار

### طبقات Clean Architecture

```
Brqosh.Domain          ← كيانات + قواعد أعمال، صفر تبعيات خارجية
Brqosh.Application     ← حالات استخدام، واجهات مستودعات، تحقق
Brqosh.Infrastructure  ← EF Core/PostgreSQL، ZATCA، تقارير، ملفات
Brqosh.Desktop         ← WPF/MVVM، لا منطق أعمال في الواجهة
Modules/*              ← وحدات نظام العمل (تعتمد على Application فقط)
```

اتجاه الاعتماد دائماً نحو الداخل: Desktop → Application → Domain.

### أنظمة العمل (Business Profiles)

| Profile | الوحدات المُفعَّلة |
|---|---|
| construction | GL، مشاريع/BOQ/مستخلصات، مشتريات، خزينة، تقارير |
| manufacturing | GL، BOM/أوامر إنتاج/WIP، مخزون، مشتريات، تقارير |
| retail | GL، POS/باركود، مبيعات، مخزون، خزينة، تقارير |
| general | GL، خزينة، تقارير (محاسبة عامة) |

### قواعد غير قابلة للتفاوض

1. **GL (النواة المحاسبية) لا تُعطَّل أبداً** — أي محاولة تعطيل ترمي استثناء.
2. التعطيل = إخفاء وتعليق فقط — **لا حذف بيانات، لا حذف صلاحيات**.
3. كل وحدة تعلن: صفحاتها، صلاحياتها، تقاريرها، وتبعياتها — عبر واجهة `IModuleDefinition`.
4. التفعيل محفوظ على مستوى الشركة (multi-company) مع دعم فروع.

## الأداء (هدف تصميمي منذ اليوم الأول)

- جداول الحركات (قيود، فواتير، حركات مخزون) مقسّمة **partitions حسب السنة المالية**.
- كل الشاشات تستخدم **pagination من الخادم** (50–100 صف) — ممنوع تحميل جدول كامل.
- التقارير الثقيلة عبر Dapper + استعلامات SQL مكتوبة يدوياً.
- فهارس مركبة: (company_id, entry_date, account_id) وما شابه.
- أهداف قابلة للقياس: إقلاع < 3s، فتح شاشة < 500ms، بحث في 5M < 1s.
