### P0-02 — VAT و ZATCA للمستخلصات والمقاولات

#### الوصف
مستخلصات الأعمال (`ProgressBilling`) تُرحَّل محاسبياً كإيراد عقد بلا ضريبة قيمة مضافة، ولا تدخل إقرار VAT، ولا يُولَّد لها XML ZATCA.

**2. إقرار VAT — يتجاهل المستخلصات:**

#### هل يدخل إقرار VAT؟
**لا.** `VatReturnQuery` لا يقرأ `progress_billings`.

#### هل يُولَّد XML مطابق؟
**لا.** لا يوجد مسار توليد.

#### السيناريو

شركة مقاولات بملف `BusinessProfile.Construction`:
1. تُرحّل مستخلص بقيمة 1,000,000 ريال (أعمال حالية).
2. القيد: مدين ذمم 900,000 + محتجز 100,000 / دائن إيراد 1,000,000.
3. **ضريبة مخرجات مفقودة:** 150,000 ريال غير مُسجَّلة.
4. إقرار VAT يُظهر 0 من هذا المستخلص.
5. لا مستند ZATCA — مخالفة عند الفحص.

### P0-04 — حماية نظام الترخيص

#### الوصف
نظام الترخيص يعتمد HMAC-SHA256 بمفتاح سري **مُضمَّن في الكود المصدري**. الأخطر: `ValidateForCompany` يحتوي fallback يُقارن المفتاح المُولَّد بنفسه — **ينجح دائماً**.

#### الأدلة

**المفتاح السري في الكود:**

```11:11:src/Brqosh.Infrastructure/Licensing/LicenseService.cs
    private const string Secret = "BRQOSH-ERP-LICENSE-KEY-2026";
```

**توليد المفتاح (أي شخص لديه الكود):**

```20:25:src/Brqosh.Infrastructure/Licensing/LicenseService.cs
    public static string GenerateKey(string companyName, string machineId)
    {
        var payload = $"{companyName.Trim()}|{machineId}";
        using var hmac = new HMACSHA256(Encoding.UTF8.GetBytes(Secret));
        return Convert.ToHexString(hmac.ComputeHash(Encoding.UTF8.GetBytes(payload)));
    }
```

**Fallback الذي يُبطل الحماية:**

```34:44:src/Brqosh.Infrastructure/Licensing/LicenseStore.cs
    public static bool ValidateForCompany(string companyName)
    {
        var machineId = LicenseService.MachineId();
        var stored = Load();
        if (stored is not null &&
            LicenseService.Validate(stored.CompanyName, stored.MachineId, stored.LicenseKey))
            return true;

        return LicenseService.Validate(companyName, machineId,
            LicenseService.GenerateKey(companyName, machineId));
        // ↑ يولّد المفتاح ثم يتحقق منه — النتيجة دائماً true
    }
```

**تجاوز تلقائي عند التشغيل:**

```77:86:src/Brqosh.Desktop/App.xaml.cs
        LicenseStore.EnsureTrialKey(setup!.CompanyName);  // يولّد ويحفظ مفتاحاً تلقائياً
        if (!LicenseStore.ValidateForCompany(setup.CompanyName))
        {
            var license = new LicenseActivationWindow(...);  // لن يُستدعى عملياً
        }
```

`EnsureTrialKey` (سطور 46-52 في `LicenseStore.cs`): إذا لا يوجد `license.json`، يُنشئ مفتاحاً صالحاً ويحفظه.

#### هل يستطيع شخص لديه نسخة البرنامج إنشاء تراخيص؟

**نعم — بسهولة تامة.**

**السيناريو 1 — بدون أي أدوات:**
1. تشغيل البرنامج → `EnsureTrialKey` يُنشئ ترخيصاً تلقائياً.
2. `ValidateForCompany` → `true` دائماً.
3. **لا تظهر شاشة التفعيل أبداً.**

**السيناريو 2 — مع الكود المصدري أو decompile:**
1. قراءة `Secret = "BRQOSH-ERP-LICENSE-KEY-2026"`.
2. حساب `MachineId()` = SHA256(`MachineName|UserName|OSVersion`)[0..16].
3. `GenerateKey("اسم الشركة", machineId)` → مفتاح صالح لأي جهاز.

**السيناريو 3 — تزوير ملف الترخيص:**
- الملف: `%APPDATA%\BRQOSH\license.json` — JSON بلا توقيع أو حماية.
- يمكن تعديله يدوياً؛ حتى مع مفتاح خاطئ، fallback يمرّر التحقق.

#### التخزين
| العنصر | الموقع | الحماية |
|--------|--------|---------|
| Secret HMAC | كود مصدري | **لا شيء** |
| license.json | %APPDATA%\BRQOSH\ | **لا تشفير** |

#### مستوى الخطورة
**حرجة** — نظام الترخيص **غير فعّال كحماية تجارية**.

#### هل تحتاج إصلاح؟
**نعم** إذا كان الترخيص نموذج عمل. إذا كان شكلياً فقط، يجب توثيق ذلك صراحة.

#### الإصلاح المقترح (دون تنفيذ)
- إزالة fallback الذاتي من `ValidateForCompany`.
- نقل السر لخادم ترخيص أو توقيع RSA غير متماثل.
- عدم تضمين Secret في الكود المُوزَّع.
- تشفير `license.json` أو ربطه بـ DPAPI.

### P0-05 — SQLite Fallback

#### الوصف
عند فشل اتصال PostgreSQL، ينتقل النظام **تلقائياً** إلى SQLite المحلي دون إيقاف التشغيل. لا يوجد `Environment Mode` (Development/Production) يتحكم بهذا السلوك.

#### الأدلة

**الافتراضي بدون إعداد:**

```21:32:src/Brqosh.Desktop/AppServices.cs
    private static DatabaseProvider _provider = DatabaseProvider.Sqlite;
    private static string _connectionString = $"Data Source={BrqoshDbContextFactory.DefaultSqlitePath()}";
    // إذا لا يوجد database.json → SQLite مباشرة
```

**Fallback عند فشل PostgreSQL:**

```59:75:src/Brqosh.Desktop/AppServices.cs
    public static async Task EnsureDatabaseReachableAsync()
    {
        if (_provider != DatabaseProvider.PostgreSql)
            return;
        try { /* OpenConnection */ }
        catch
        {
            _provider = DatabaseProvider.Sqlite;
            _connectionString = $"Data Source={BrqoshDbContextFactory.DefaultSqlitePath()}";
            _usingFallbackSqlite = true;
        }
    }
```

**تنبيه المستخدم — تحذير فقط، لا إيقاف:**

```69:74:src/Brqosh.Desktop/App.xaml.cs
        if (AppServices.UsingFallbackSqlite)
        {
            MessageBox.Show("تعذر الاتصال بـ PostgreSQL — تم التبديل تلقائياً إلى SQLite المحلي.\n...");
        }
        // البرنامج يستمر → MainWindow
```

**بحث `Environment|Production|Development` في `AppServices` و`App.xaml.cs` → لا وضع بيئة مُعرَّف.**

#### متى يحدث الانتقال؟

| الحالة | السلوك |
|--------|--------|
| لا `database.json` | SQLite من البداية (ليس fallback لكن نفس المخاطر) |
| `database.json` = PostgreSQL + خادم متوقف | **Fallback صامت** + MessageBox تحذير |
| `database.json` تالف | SQLite (سطر 50-53) |

#### هل يمكن أن يعمل Production على SQLite بالخطأ؟

**نعم — سيناريوهان:**
1. عميل لم يُعدّ `database.json` → SQLite افتراضياً بلا تحذير fallback.
2. عميل أعدّ PostgreSQL لكن الخادم تعطل مؤقتاً → بيانات تُكتب في SQLite محلي **منفصل** عن PostgreSQL.

#### مخاطر السلوك

| المخاطرة | الخطورة |
|----------|---------|
| تعدد مستخدمين على SQLite — قفل ملف | حرجة |
| فقدان بيانات عند خلط SQLite/PostgreSQL | حرجة |
| نسخ احتياطي Enterprise على PG بينما التشغيل الفعلي SQLite | حرجة |
| عدم اكتشاف المشكلة إذا تجاهل المستخدم التحذير | عالية |

#### مستوى الخطورة
**حرجة** لبيئة إنتاج متعددة المستخدمين.

#### هل تحتاج إصلاح؟
**نعم.**

#### الإصلاح المقترح (دون تنفيذ)
- `AppMode: Production` → فشل صريح بدون fallback.
- `Development` → يسمح SQLite.
- تسجيل (log) عند كل fallback.
- منع التشغيل إذا `database.json` يحدد PostgreSQL والاتصال فاشل.

#### اختبار منطقي للأحجام

افتراض: متوسط 3 سطور/حركة، ~500 بايت/كيان محمّل ≈ 1.5 KB/حركة.

| عدد الحركات | حجم تقريبي/استعلام | زمن تقديري (قرص SSD) | التأثير |
|-------------|-------------------|---------------------|---------|
| **100,000** | ~150 MB في الذاكرة | 2-10 ثوانٍ/استعلام | بطء ملحوظ في البيع |
| **1,000,000** | ~1.5 GB | 20-120 ثانية أو OOM | **غير عملي** |
| **10,000,000** | ~15 GB | OOM مؤكد | **تعطّل** |

**مثال عملية بيع واحدة** (5 أصناف، 3 مستودعات، 500K حركة تاريخية):
- التحقق من الرصيد: 5 × تحميل 500K حركة
- `ApplyReceiptCostAsync`: 3 مستودعات × 500K لكل صنف وارد
- **تقدير: 15+ تحميل كامل للجدول** لعملية واحدة.

#### الاستعلامات الثقيلة الأخرى (مرتبطة)

| الاستعلام | الملف | المشكلة |
|-----------|-------|---------|
| `GetOnHandAsync` | `InventoryService.cs:30-32` | الأشد |

#### مستوى الخطورة
**حرجة** عند التوسع؛ **متوسطة** حالياً لبيانات صغيرة (&lt;10K حركة).

#### هل تحتاج إصلاح؟
**نعم** قبل أي عميل بحجم بيانات متوسط.

#### الحل المعماري المقترح (دون تنفيذ)
1. **جدول أرصدة** `inventory_balances (company_id, warehouse_id, product_id, qty_on_hand)` يُحدَّث عند كل ترحيل.
2. أو استعلام SQL مجمّع:

3. فهرس `(CompanyId, Status, WarehouseId)` على `stock_movements`.
4. إبطال cache per-request لتجنب التحميل المتكرر في نفس العملية.
