## 1. ما هو BRQOSH فعلاً

نظام **ERP محاسبي سعودي** بـ .NET 9 / WPF (RTL) / EF Core / Clean Architecture، يبدأ باختيار **نظام عمل** (مقاولات/إنتاج/تسويق…) فيفعّل الوحدات المناسبة فوق نواة محاسبية مشتركة، مع مسار امتثال ZATCA المرحلة الثانية.

**الحجم الفعلي:** Domain 87 ملفاً (6,054 سطراً) · Application 24 · Infrastructure 192 (24,066 سطراً) · Desktop 157 (17,086 سطراً) + 124 XAML · Api 4 (778 سطراً) · **510 اختباراً** عبر 4 مشاريع.

**تقدير النضج الذاتي في وثائقهم (`ROADMAP.md`): ~32–40% جاهزية سوقية** — وهو تقدير **صادق ومطابق** لما وجدناه.

## 2. نقاط القوة الحقيقية (بدليل)

هذه ليست مجاملة — كل نقطة مرصودة بكود:

1. **القيد المزدوج محصّن في العمق.** `JournalEntry.Post()` يرفض أي قيد غير متوازن نصاً، و`AddLine` يمنع السالب والمدين-الدائن معاً والسطر الصفري والترحيل على حساب تجميعي. القيد المرحّل **لا يُعدَّل أبداً** — التصحيح بقيد عكسي فقط. ومختبَر على مستويين: الدومين + خدمات تختم كل سيناريو ذهبي بـ `Assert.Equal(tb.Debit, tb.Credit)`.
2. **تخزين كلمات المرور احترافي.** PBKDF2-SHA256، 100,000 دورة، ملح 16 بايت لكل تجزئة، `FixedTimeEquals`، ترقية تلقائية من SHA-256 القديم. سياسة كلمة مرور صارمة (12 حرفاً + تعقيد + قائمة حظر).
3. **فرض الأدوار مزدوج ومحكم.** إخفاء عند بناء القائمة + إعادة فحص عند كل تنقل، بلا مسار بديل لإنشاء شاشة محظورة، مع دفاع-في-العمق على طبقة الخدمات (`SecurityContext` fail-closed، وتجاوز الاختبار مُعطَّل قسرياً في الإنتاج).
4. **المعاملات متينة فعلاً.** كل ترحيل مالي (فاتورة + قيد + مخزون + تدقيق + توليد ZATCA XML) داخل `UnitOfWork.ExecuteInTransactionAsync` واحد، مستخدَم في 39 خدمة. والإرسال الخارجي لـ ZATCA **بعد** الـ commit عمداً.
5. **سقف إشعار الدائن تراكمي.** يجمع الإشعارات السابقة على نفس الفاتورة ويرفض التجاوز، مع اختبار مخصص وحارس اختلاف العميل.
6. **ZATCA كود حقيقي لا ادعاء.** UBL 2.1 + توقيع XAdES-EPES (EC P-256) + QR TLV + CSID + إرسال HTTP فعلي + أسرار محمية بـ DPAPI.
7. **اتجاه مراجع المشاريع سليم 100%.** Domain نقيّ بلا أي تبعية، Application → Domain فقط، لا دورات.
8. **انضباط توثيقي نادر.** تعريف رباعي المستويات لكلمة «مغلق»، 182 تقرير CEEF مرقّم، تقدير جاهزية صادق.

## 3. الثغرات الحرجة (🔴 محقَّقة يدوياً — تمنع الإنتاج)

### 🔴 ح-1: استعادة كلمة المرور تعرض رمز OTP على الشاشة نفسها → استيلاء كامل على أي حساب

**الملفات:** `WhatsAppNotificationChannel.cs:18` · `OtpHintFormatter.cs:8` · `WhatsAppNotificationChannelFactory.cs:7`

**تأكيد مباشر:** `InAppOtpNotificationChannel.SendOtp` يُرجع الرمز الحقيقي كـ `DevHint`، و`OtpHintFormatter.Format` يعرضه نصاً: `$"رمز التحقق: {result.DevHint}"`. المصنع يُرجع **دائماً** `InAppOtpNotificationChannel` — لا قناة خارجية، **ولا أي بوابة `IsProduction`** على العرض.

**الأثر:** أي شخص أمام شاشة الدخول يكتب اسم مستخدم نشط (بما فيه المدير) في «نسيت كلمة المرور» → يرى الرمز على الشاشة → يعيد التعيين ويستولي على الحساب. تجاوز كامل للمصادقة، يعمل في الإنتاج.

**العلاج:** بوابة بيئة تمنع `DevHint` خارج التطوير (كما فُعل مع `AutomatedTestBypass`)، أو ربط قناة إرسال حقيقية (SMS/WhatsApp Business)، أو حصر إعادة التعيين بيد المدير. **أولوية قصوى.**

### 🔴 ح-2: هجرات EF مولّدة بأنواع SQLite → مخطط معطوب على PostgreSQL إنتاجي جديد

**الملف:** `Migrations/20260707000538_InitialCreate.cs:18` (وأخواتها)

**تأكيد مباشر:** كل الأعمدة `Id` بنوع `"INTEGER"` + `.Annotation("Sqlite:Autoincrement", true)`، وكل النصوص والتواريخ `"TEXT"`. ومصنع وقت التصميم مثبَّت على SQLite. إن هُيّئت قاعدة PostgreSQL جديدة عبر `MigrateAsync`، سيتجاهل Npgsql وسم `Sqlite:Autoincrement` فتُنشأ أعمدة `Id` بلا identity → أول إدراج شركة يفشل، والتواريخ `TEXT` تكسر المقارنات.

**الأثر:** تثبيت إنتاجي نظيف على PostgreSQL **لا يعمل** عبر مسار الهجرات. هذا على الأرجح سبب وجود `tools/DbStartupProbe` أصلاً، واعتماد النظام على `EnsureCreated` + `BrqoshSchemaUpdater` اليدوي (1,303 سطراً) كمسار فعلي — انظر ع-2.

**العلاج:** أعد توليد الهجرات ضد Npgsql (أو هجرات لكل مزوّد)، غيّر مصنع وقت التصميم، وأضف اختبار تكامل يبني PG فارغة عبر `MigrateAsync` ويرحّل فاتورة كاملة.

### 🔴 ح-3: حارس ثبات سجل التدقيق لا يعمل على مسار سطح المكتب (المنتج الأساسي)

**الملف:** `Persistence/DbContextFactory.cs:23`

**تأكيد مباشر:** `BrqoshDbContextFactory.Create` يبني الخيارات بـ `ConfigureWarnings` فقط — **بلا `AddInterceptors`**. المعترض `AuditLogImmutabilityInterceptor` يُضاف فقط في مسار DI (`InfrastructureServiceCollectionExtensions.cs:48`). وسطح المكتب ينشئ السياق عبر `AppServices.CreateDb()` → المصنع مباشرة.

**الأثر:** كل عمليات Desktop تمر بسياقات بلا حارس ثبات — يمكن تعديل/حذف `AuditLogEntry` برمجياً دون اعتراض. وعد «Immutable Audit Ledger» مفروض فقط على مسار API الثانوي.

**العلاج:** أضف `AddInterceptors(new AuditLogImmutabilityInterceptor())` داخل `Create` نفسه، وادرس فرض الثبات في القاعدة (REVOKE UPDATE/DELETE أو trigger) لأن اعتراض EF لا يحمي من SQL خام.

## 4. الثغرات العالية (🟠 مرتبة بالمخاطرة)

### أمن واجهة API (رأس SaaS — 4 ثغرات مترابطة)
- **ع-A1** `Program.cs:401,230`: نقطتا `/companies` و`/company-groups` لا تطبقان عزل المستأجرين → حامل المفتاح المشترك يحذف ترويسة `X-Tenant-Id` فيسرد **كل** الشركات وأرقامها الضريبية.
- **ع-A2** `Program.cs:118`: هوية المستأجر **مُعلَنة ذاتياً** بترويسة `X-Tenant-Id` فوق مفتاح API واحد مشترك — لا ربط بين المفتاح والمستأجر.
- **ع-A3** `ApiSecurityContextMiddleware.cs:18`: كل مستدعي API يحصل **افتراضياً على دور Administrator**، والدور من ترويسة يتحكم بها العميل → انتحال هوية في سجل التدقيق.
- **ع-A4** `Program.cs:153`: كاش Idempotency عالمي غير معزول → مستأجر يستلم جسد استجابة مستأجر آخر.
- **العلاج الجذري:** مفاتيح API لكل مستأجر مخزّنة (مجزّأة)، اشتقاق `TenantId` والدور من المفتاح المصادَق لا من ترويسة، ودمج `TenantId` في مفتاح الكاش. *(هذه المخاطر تخص وضع SaaS؛ في التشغيل المكتبي أحادي المستأجر أثرها أقل لكنها تبقى ديناً قبل أي إطلاق سحابي.)*

### امتثال ZATCA (يعمل محلياً، يُرفض لدى الهيئة)
- **ع-Z1** `ZatcaEInvoiceGenerator.cs:258`: استبدال QR **بعد** التوقيع بينما الهاش لا يستثني عنصري QR و`cac:Signature` → توقيع يُبطِل نفسه، ترفضه الهيئة.
- **ع-Z2** `ZatcaUblInvoiceBuilder.cs:66`: UBL ناقص `cac:TaxSubtotal` وعنوان البائع و CRN (إلزامية BR-CO-18/KSA) → رفض في الإنتاج.
- النظام يعمل حالياً فقط لأن **وضع المحاكاة يقبل محلياً دون فحص**. يُضاف نقص ترويسة `Accept-Version: V2` وتضارب تقريب السطر/المستند.

### التقارير المالية
- **ع-R1** `BalanceSheetQuery.cs:51`: الميزانية تضيف أرباح **السنة الجارية فقط** — أي سنة سابقة لم يُشغَّل إقفالها اليدوي تترك الميزانية **مختلة** طوال السنة التالية.
- **ع-R2** `IncomeStatementQuery.cs:25`: قائمة الدخل لا تستبعد قيد الإقفال السنوي → قائمة أي سنة مقفلة تعود **صفراً**.

### البيانات والتزامن
- **ع-D1** `InventoryService.cs:288`: **غياب تام لرموز التزامن** في المشروع كله + تحديث رصيد المخزون قراءة-ثم-كتابة → ضياع تحديثات تحت التزامن (وهدف المنتج متعدد المستخدمين).
- **ع-D2** `PersistingDomainEventPublisher.cs:42`: الأحداث والويبهوكس تُكتب/تُرسل **خارج** معاملة الترحيل (لا Outbox) → حدث زائف عن فاتورة مرتدّة.
- **ع-D3** `AppServices.cs:146`: البيئة الافتراضية Development + **تحويل صامت** من PostgreSQL إلى SQLite عند فشل الاتصال → «انقسام دماغي محاسبي» بلا إنذار.

### المعمارية (دَين مُقاس، لا عطل)
- Desktop يتخطى Application ويكلم EF مباشرة (156 استدعاء `CreateDb` في 93 ملفاً، 43 `SaveChanges` في 34 code-behind، لا ViewModels رغم ادعاء MVVM).

- Application طبقة **قشرة** (تسجيل DI فارغ صراحة)؛ كل التنفيذ في Infrastructure.
- *حملة CEEF بدأت التصحيح فعلاً (DI scope + 13 واجهة استعلام) لكنها لم تكتمل.*

**المخاطر:**
1. `git clean -fd` أو عطل قرص واحد = **فقدان أسابيع عمل نهائياً**.
2. commit للمرحّل وحده = **مستودع لا يُبنى** (الـ sln يشير لمشروع Api غير متتبع).
3. **ملوثات جاهزة للانجراف** في أي `git add -A`: `dist/` (391MB ثنائيات غير مُتجاهلة)، `system_prompts_leaks-main/` (9.6MB)، وملفات برومبتات AI في الجذر.

**العلاج الفوري:** أضف `dist/` و`system_prompts_leaks-main/` إلى `.gitignore`، ثم سلسلة commits موضوعية (أمن → قاعدة → كل وحدة باختباراتها → أدوات/وثائق) مع `.gitattributes` يوحّد نهايات الأسطر. **افعلها قبل أي شيء آخر — هذا الخطر الوحيد الذي يُفقِد العمل.**
