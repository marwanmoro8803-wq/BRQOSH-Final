## ملخص تنفيذي

BRQOSH نظام ERP سطح مكتب (WPF / .NET 9) بغطاء وظيفي واسع: محاسبة عامة، مبيعات، مشتريات، مخزون، خزينة، ZATCA، مقاولات، تصنيع، POS، أصول، رواتب. **البناء والاختبارات الوحدوية ناجحة** (115 اختبار، 0 فشل). المنطق المحاسبي في طبقة Domain قوي نسبياً، مع مراجعات QA موثّقة في `docs/ROADMAP.md`.

**لكن النظام ليس جاهزاً للإنتاج بثقة كاملة.** توجد فجوات حرجة في: الأمان (بيانات اعتماد افتراضية، ترخيص قابل للكسر)، سلامة المعاملات (غياب Transactions)، أداء المخزون عند التوسع، امتثال ضريبي لمستخلصات الأعمال، وغياب CI/تدقيق UI مُثبت في هذه الجلسة.

**الحكم:** نظام متقدم في مرحلة **ما قبل الإنتاج (Pre-Production)** — مناسب للتجريب الداخلي والتدقيق، وليس للنشر التجاري دون معالجة الأولويات الحرجة.

### 2.1 ما تم فحصه

- ~418 ملف `.cs` في `src/`
- ~81 ملف XAML في Desktop
- أنماط الخدمات، التكرار، التعقيد

### 2.2 جودة الكود

**إيجابيات:**
- Nullable مفعّل، تعليقات عربية مفيدة في Domain
- قواعد محاسبية في الكيانات (`JournalEntry`, `SalesInvoice`) وليس فقط في UI
- `AccountingException` موحّد
- `UiFeedback` لمعالجة أخطاء موحّدة في التقارير
- لا توجد علامات `TODO`/`FIXME`/`HACK` في `src/` (إما نظيف أو الديون غير موثّقة)

**سلبيات:**
- `MainWindow.xaml.cs`: switch ضخم (~50 case) للتنقل — anti-pattern
- تكرار نمط `SaveChangesAsync` مزدوج في خدمات الترحيل (حفظ للحصول على Id ثم ربط)
- `AppServices` static global state (`CompanyId`, `CurrentUser`, `CurrentShiftId`)
- كل صفحة تنشئ `DbContext` جديداً بدون DI container
- لا يوجد `IDisposable` pattern موحّد للصفحات مع DbContext

### 2.3 الديون التقنية الرئيسية

## 3. قاعدة البيانات

### 3.1 ما تم فحصه

- `BrqoshDbContext.cs` (557 سطر)
- Migrations (4 + Initial)
- `docs/postgres-partitioning.sql`

### 3.2 التصميم

- **32 كيان** في DbContext يغطي كل وحدات ERP
- جداول بأسماء snake_case عبر `ToTable()`
- `OwnsMany` لسطور المستندات (فواتير، قيود، BOM...)
- `decimal(18,2)` للمبالغ، `decimal(18,4)` للكميات — مناسب

### 3.3 الفهارس (جيد)

- فهارس مركبة `(CompanyId, Code)` فريدة على البيانات الأساسية
- `(CompanyId, EntryDate)` على القيود — جاهز للتقسيم
- `(CompanyId, InvoiceNumber)` فريد على الفواتير

### 3.4 القيود والعلاقات (ضعيف)

- **9 مراجع `HasForeignKey` فقط** — أغلبها لـ `OwnsMany`
- **لا توجد FK صريحة** بين `SalesInvoice.CustomerId` → `customers` مثلاً
- **لا RowVersion / Concurrency Token** — تعارضات الكتابة المتزامنة غير مُدارة
- **لا `BeginTransaction`** في أي مكان في `src/` — مُتحقَّق بالبحث

#### ق-01: غياب المعاملات (Transactions)

| البند | التفاصيل |
|-------|----------|
| **السبب** | كل `PostingService` يستدعي `SaveChangesAsync` متعددة بدون `BeginTransaction` |
| **التأثير** | فشل جزئي محتمل: قيد مُرحَّل بدون فاتورة، أو فاتورة بدون حركة مخزون |
| **الخطورة** | **حرجة** |
| **الحل المقترح** | `await using var tx = await db.Database.BeginTransactionAsync()` في كل عملية مركّبة |

**مثال:** `SalesInvoicePostingService.PostAsync` يحفظ القيد والفاتورة، ثم يحفظ الربط، ثم يصدر المخزون منفصلاً.

#### ق-02: ضعف سلامة المرجعية على مستوى DB

| البند | التفاصيل |
|-------|----------|
| **السبب** | EF يعتمد على منطق التطبيق فقط لسلامة الروابط |
| **التأثير** | سجلات يتيمة عند أخطاء أو تعديل مباشر للDB |
| **الخطورة** | عالية |
| **الحل المقترح** | إضافة FK constraints في migrations |

#### ق-03: Soft Delete غير شامل

| البند | التفاصيل |
|-------|----------|
| **السبب** | `HasQueryFilter` على بعض الكيانات فقط (accounts, customers, products...) |
| **التأثير** | سلوك حذف غير متسق بين الوحدات |
| **الخطورة** | متوسطة |
| **الحل المقترح** | توحيد `ISoftDeletable` + filter شامل أو توثيق الاستثناءات |

#### ق-04: SQLite كبديل تلقائي

| البند | التفاصيل |
|-------|----------|
| **السبب** | `AppServices.EnsureDatabaseReachableAsync` يتحول لـ SQLite عند فشل PostgreSQL |
| **التأثير** | بيئة إنتاج قد تعمل على SQLite بدون علم المستخدم — لا يصلح لتعدد المستخدمين |
| **الخطورة** | **حرجة** (إنتاج) |
| **الحل المقترح** | في Production: فشل صريح بدلاً من fallback صامت |

### 3.5 الأداء المتوقع

- **جيد:** `TrialBalanceQuery` يُجمع على مستوى DB (`GroupBy` على سطور القيود)
- **سيء:** `InventoryService.GetOnHandAsync` يحمّل **كل** حركات المخزون المرحّلة للشركة إلى الذاكرة ثم يحسب في C# — O(n) لكل استعلام رصيد
- **متوسط:** `GeneralLedgerQuery`, `VatReturnQuery`, `CustomerBalanceQuery` تحمّل مستندات كاملة إلى الذاكرة
- **التقسيم:** موثّق يدوياً في `docs/postgres-partitioning.sql` — **غير مُطبَّق** في الكود

## 6. الأمن

### 6.1 المصادقة

- PBKDF2-SHA256 بـ 100,000 iteration — **جيد**
- ترقية تلقائية من SHA-256 القديم — جيد
- **مستخدم افتراضي `admin` / `admin123`** يُنشأ تلقائياً
- **كلمة المرور مُعبَّأة مسبقاً** في `LoginWindow.xaml.cs`
- **نص مرئي في UI:** «المستخدم الافتراضي: admin / admin123»

#### أ-01: بيانات اعتماد افتراضية معروفة

| السبب | `UserAuthService.EnsureDefaultAdminAsync` + LoginWindow |
| التأثير | اختراق فوري لأي تثبيت لم يُغيَّر |
| الخطورة | **حرجة** |
| الحل | إجبار تغيير كلمة المرور عند أول دخول؛ إزالة التعبئة المسبقة |

### 6.2 الصلاحيات

- `PermissionService`: RBAC على مستوى **الشاشات فقط**
- **لا فرض على مستوى الخدمات** — أي استدعاء مباشر للـ Infrastructure يتجاوز الصلاحيات
- 4 أدوار: Administrator, Accountant, Cashier, Viewer
- شاشات غير المعروفة = مرفوضة ✅

#### أ-02: صلاحيات UI-only

| السبب | لا يوجد `IAuthorizationService` في Infrastructure |
| التأثير | تجاوز الصلاحيات عبر أدوات خارجية أو تعديل مستقبلي |
| الخطورة | عالية |
| الحل | فرض `CanPerform(action)` في كل `*Service` |

### 6.3 الترخيص

- HMAC-SHA256 على `MachineName|UserName|OS`
- **المفتاح السري مُضمَّن في الكود:** `BRQOSH-ERP-LICENSE-KEY-2026`

#### أ-03: سر الترخيص في الكود المصدري

| السبب | `LicenseService.Secret` ثابت |
| التأثير | أي شخص يقرأ الكود يولّد مفاتيح ترخيص |
| الخطورة | **حرجة** (نموذج تجاري) |
| الحل | توقيع غير م simmetric خارجي أو خادم ترخيص |

### 6.4 حماية البيانات

- `database.json` في `%APPDATA%` — connection string **نص صريح**
- SQLite DB في AppData — **بدون تشفير**
- لا backup/restore مدمج
- سجل تدقيق (`AuditLogEntry`) على عمليات حساسة — **جيد** لكن غير شامل لكل CRUD
